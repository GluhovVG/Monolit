# AGENTS.md — MONOLITH: правила разработки для бухгалтера и ИИ

> Этот файл — рабочие правила изменения исходного кода, а не утверждённая бухгалтерская методика. Целевой состав отчётности: [docs/ACCOUNTING_OUTPUT_SPEC.md](docs/ACCOUNTING_OUTPUT_SPEC.md). Ревью: [docs/ADAPTIVE_CODE_REVIEW_2026-10-21.md](docs/ADAPTIVE_CODE_REVIEW_2026-10-21.md).

## 1. Главная цель
MONOLITH должен воспроизводимо собирать управленческий финансовый результат **по каждой сделке, финансовому блоку, заказчику, месяцу, кварталу и году**, с детализацией плана и факта. Excel «Управленческий учет 2025» — **образец структуры отчёта**, но не безусловно верная методика: в исходном файле есть повреждённые ссылки и ошибки деления на ноль.

Не начинай с красивого дашборда. Начинай с точной модели показателей, подтверждённых источников и тестов арифметики.

## 2. Порядок работы бухгалтера-разработчика
1. Описать на русском языке, что нужно изменить и какой пользовательский результат ожидается.
2. Найти **первичный источник** (1С, ОПП, завод, сторонний производитель, документы, комплектация, доставка, СМР) и точные поля; не угадывать по названию колонки.
3. Написать пример на **искусственных** числах: ввод → формула → результат, включая крайний случай.
4. Добавить автоматический тест или контрольный пример *до* правки формулы.
5. Внести минимальное изменение. Не изменять одновременно несвязанные экраны и методики.
6. Запустить typecheck, тесты, сборку; записать команду и фактический результат.
7. Провести Adaptive Code Review (режим DEEP для денег, доступа, импорта, CI), перечислить факты и непроверенное.
8. Показать diff ответственному за методику/инженеру. **Ни один ИИ не подтверждает бухгалтерские итоги сам.**
9. Не сливать в main, не публиковать и не развёртывать без отдельного разрешения.

## 3. Финансовые инварианты (не менять без утверждения)
- **Выручка, себестоимость, прибыль, вес** — разные типы показателей; рубли не складывают с килограммами или тоннами.
- **Прибыль = выручка − полная себестоимость**. Себестоимость должна раскладываться по статьям без двойного учёта.
- **Рентабельность продаж = прибыль / выручка × 100%**; **наценка = прибыль / себестоимость × 100%**. Это НЕ одно и то же.
- **Отклонение, ₽ = факт − план**; **индекс выполнения = факт / план**; **отклонение, % = (факт − план) / план × 100%**. Договориться о знаке «экономии» отдельно: экономия затрат = план затрат − факт затрат.
- Нулевая база для деления ⇒ **«не рассчитывается» (null)**, никогда `Infinity`, `NaN`, пустая строка, маскирующая ошибку, или автоматически 0%.
- Нет исходного документа/значения ⇒ `null` / статус **«Нет данных»**, а не 0. Достоверный ноль фиксируется отдельно с источником.
- Учитывать **план и факт по каждому финансовому блоку** отдельно: МК, документация, комплектация, доставка, СМР. БГ и штрафы — отдельная статья, а не шестой доходный блок по умолчанию.
- Вес хранить с явной единицей; конверсия **1 т = 1000 кг** только на явно названной границе; цена ₽/кг не должна случайно стать ₽/т.
- НДС: признак **с НДС / без НДС** обязателен у исходной суммы. Не складывать несопоставимые базы; ставка и способ исключения НДС — только утверждённые параметры, не константа по догадке.
- Проценты — не рубли: коэффициент 0,15, 15%, «индекс выполнения 1,15» различаются; формат отображения не меняет семантику.
- Агрегировать **сначала суммы**, потом вычислять рентабельность по суммам. Не усреднять проценты сделок как общий процент без утверждённого взвешивания.
- Не округлять промежуточные вычисления на каждом шаге. Для бухгалтерских денег использовать точный десятичный тип/копейки, если бизнес-операция этого требует; решение документировать и тестировать.
- Отрицательные суммы могут быть сторно/возвратом. Не запрещать их глобально, пока не определена бизнес-семантика.
- Поощряется строгая модель `period = YYYY-MM`; накопительный итог — сумма доступных подтверждённых периодов с указанием неполных данных. Не выдавать «нет данных» за «0».
- При изменении источника, правила или привязки ОПП сбрасывается статус подтверждения **затронутых** расчётов и сохраняется прежняя версия.
- Порог существенности (например 50 000 ₽ / 2%) — черновое предложение; **логика ИЛИ/И и база процента** должны быть утверждены, прежде чем блокировать реальные записи.

## 4. Данные и связь между листами/источниками
- Основной ключ сделки — стабильный **шифр/ID**, а не имя заказчика или строка изделия. Для одноимённых шифров разных периодов нужен составной бизнес-ключ.
- Все связи (ОПП, CRM/B24, завод, сторонние, проектирование, комплектация, доставка, СМР) проходят через проверенный справочник сопоставлений; неоднозначность — конфликт, не автоматический выбор первого результата.
- Отдельные сущности: `Deal`, `Period`, `SourceFileVersion`, `BlockPlanFact`, `CostItem`, `CalculationVersion`, `ReviewIssue`, `ApprovalDecision`.
- Хранить ссылку на файл/версию и строку, дату, автора, единицу измерения, признак НДС, правило расчёта, промежуточные значения, итог.
- Статусы: `нет данных → черновик → проверка → подтверждено`; при новых данных — вернуть только затронутые показатели на проверку.
- Источником финансовой истины должен стать **backend**; frontend только показывает ответ и временный предпросмотр, не утверждает итог.

## 5. Код без лишней сложности
- Чистые функции расчётов отдельно от React-компонентов; каждая функция отвечает за один показатель.
- Не копировать формулу в Excel-экспорт, backend и frontend три раза. Общий расчётный модуль/контракт плюс независимые golden-тесты.
- TypeScript `strict`, типы для периода, валюты, сумм, статусов и источников; проверка `tsc --noEmit`.
- Короткие функции с понятными русскими комментариями **о бизнес-смысле**, а не о синтаксисе.
- Детерминированный парсер и проверки обязательны до ИИ. ИИ может предупреждать, но не «разрешать» арифметические или сопоставительные конфликты.
- Не добавлять тяжёлые библиотеки, микросервисы или архитектурный рефакторинг без измеренной потребности (KISS/YAGNI).
- Не загружать Excel с реальными контрагентами/суммами в GitHub; только обезличенные синтетические фикстуры.

## 6. Минимальные тесты для изменения финансовой формулы
- Обычный расчёт по одному шифру, затем агрегация по блоку/периоду/заказчику.
- Ноль в знаменателе и **отсутствующее значение** — разные сценарии.
- Отрицательная корректировка, дубли строки, отсутствующий шифр, несовпадение сопоставления.
- Сумма составных частей выручки/затрат совпадает с итогом (с допуском только по документированной политике округления).
- Цена ₽/кг и вес т/кг, НДС, план/факт, маржа и наценка.
- Месячные, квартальные и накопительные итоги; неполный период не считается нулевым.
- Изменение исходника делает подтверждённый результат предварительным.
- Экспорт возвращает ту же формулу и результат, что показаны в интерфейсе.

## 7. Правило «стоп»
Остановиться и запросить бизнес-решение, если неясны: определение выручки по 1С против плановой калькуляции, НДС, отнесение затрат МК/СМР, БГ/штрафов, перенос сумм между периодами, база/знак отклонений или правило существенности. Не угадывать методику по сохранённой формуле Excel.

## 8. Ревью и контроль
Использовать приложенный пользовательский скилл **Adaptive Code Review**, сохранённый в `.agents/skills/adaptive-code-review/SKILL.md`. Режим **DEEP** для финансовых расчётов/импорта/авторизации/CI. Findings только с файлом и строкой, условием воспроизведения и проверкой; неподтверждённые гипотезы помечать отдельно. Указывать `PASS / FAIL / NOT RUN` и причину. Предусмотреть откат отдельной ветки, затем человеческое подтверждение. Тесты скилла не равны тестам MONOLITH.

## 9. Действующие ограничения проекта
- Сейчас приложение — демонстрация; настоящие источники и серверная модель учёта отсутствуют.
- GitHub: работать в отдельной ветке; `main` не менять без разрешения.
- **Не выгружать код, данные и конфигурацию в AppDeploy** без отдельного прямого указания.
